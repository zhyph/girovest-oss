# Contract Core — Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the backend half of the Contract core — the `Contract`/`Installment`/`LocationContractClause` schema, a safe migration path for existing `Allocation` rows that predate this feature, and a `contractService`/`contracts` route that lets staff create a multi-item Contract (grouping several `Allocation`s) and cancel one, with sequential per-Location contract numbering.

**Architecture:** `Contract` groups one-or-more existing `Allocation` rows (each item keeps its own checkout/return/deposit lifecycle, reusing `allocationService`'s occupancy-conflict logic) plus a flat list of `Installment` rows. `Allocation.contractId` is a genuinely new relationship for a table that already has production rows on the live desktop app (mid v0.2.3→v0.2.4 rollout) — this plan's migration strategy is deliberately conservative: the schema migration itself stays purely additive (new tables, nullable new columns, zero data manipulation, auto-generated by Prisma with no hand-edited SQL), and the actual backfill (creating one synthetic `Contract` per orphaned `Allocation`) runs as ordinary, testable TypeScript against Prisma Client at server startup — not as hand-written cross-provider migration SQL. See "Migration strategy" below for the full reasoning; this is a deliberate, documented adaptation of the original design spec's literal wording ("required FK", "run as part of the migration path"), not an oversight.

**Tech Stack:** Existing stack only — Prisma, Express, Zod, Vitest (real-DB integration style, matching `allocationService.test.ts`/`clientService.test.ts`). No new dependencies.

## Global Constraints

- No CPF/RG/country-specific logic anywhere in this plan's scope (not directly relevant here, but stays true — nothing in Contract/Installment touches client identity fields).
- Contract number sequencing must be safe under concurrent writes: the existing serializable-retry pattern from `allocationService.ts` (`MAX_WRITE_CONFLICT_RETRIES`, `Prisma.TransactionIsolationLevel.Serializable` when `DB_PROVIDER=postgresql`) is reused verbatim, backed by a DB-level `@@unique([locationId, number])` constraint as defense-in-depth.
- Every existing `Allocation` must end up with exactly one `Contract` after this plan ships and the app is run once — verified by an integration test, not just asserted.
- The default six paper-contract clauses must be seeded for both existing Locations (via the backfill) and newly-created ones (via `setupService.completeSetup`) from one shared constant, not duplicated text.
- No new npm dependencies.
- Follow existing test conventions exactly: Vitest, real-DB integration style (`beforeEach`/`afterEach` fixture creation and cleanup, matching `allocationService.test.ts`), one `describe` per unit.
- TDD: write the failing test before the implementation in every task.
- This plan is backend-only. The `NewContractForm`/`ContractsPage` UI, the required-identity/address-document inline-completion check (a frontend-only concern — the backend never blocks Contract creation on missing client documents), locking-after-signature, and remote signing are later plans.

## Migration strategy (read before Task 1)

The original design spec calls for `Allocation.contractId` to be a required FK, backfilled via a nullable-first, two-phase Prisma migration. Two problems surfaced while planning the actual SQL:

1. **SQLite has no native UUID generation and requires a full table rebuild to add a NOT NULL column to a non-empty table** (Prisma's migration engine does this automatically for schema-only changes, but a NOT NULL column populated with a *different, computed* value per row — sequential contract numbers grouped and ordered per Location — cannot be auto-generated by `prisma migrate dev`; it would need hand-written migration SQL with window functions and manual UUID generation). Hand-rolled cross-table backfill SQL is exactly the kind of place a subtle bug corrupts real data on the auto-update path this app already ships through.
2. **PostgreSQL, in this codebase, has no tracked migrations at all** (`server/prisma/postgresql/migrations/` doesn't exist — the hosted build's tests use `prisma db push`, not `migrate deploy`). A hand-written migration SQL file would only ever run for SQLite anyway, meaning the two providers would silently diverge in how (or whether) backfill happens.

**Resolution:** the schema migration (Task 1) stays purely additive — new tables, and `Allocation.contractId`/`Location.phone` added as **nullable**, auto-generated by `prisma migrate dev` with no hand-editing. The actual backfill (Task 3) is ordinary Prisma Client TypeScript, run idempotently at server startup (`server/src/server.ts`, before `app.listen`) — which happens *after* Electron's `runMigrations()` (`prisma migrate deploy`) already completed, so the new tables/columns are guaranteed to exist first. This works identically for SQLite and PostgreSQL (same Prisma Client code, no raw SQL), is trivially unit-testable against a real test database exactly like every other service in this codebase, and is idempotent (a no-op on every startup after the first).

**Consequence:** `Allocation.contractId` stays `String?` (nullable) in the Prisma schema permanently — there is no DB-level NOT NULL constraint on it. The guarantee that every Allocation has a Contract is enforced by the backfill always running before the server accepts traffic, plus every code path that creates an Allocation from this point forward (`contractService.createContract`) always providing one. This is a deliberate, narrower guarantee than a DB constraint — acceptable here because the backfill is simple, tested, and runs unconditionally on every boot, and because the alternative (hand-written cross-provider migration SQL) was assessed as materially riskier for a feature that ships through an already-live auto-update channel.

import { prisma } from '../db/client.js'
import { AppError } from '../errors/AppError.js'
import { ErrorCodes } from '../errors/errorCodes.js'
import { hashPassword } from '../auth/passwords.js'
import { DEFAULT_CONTRACT_CLAUSES } from '../constants/defaultContractClauses.js'

export interface CompleteSetupInput {
  shopName: string
  shopAddress: string
  ownerName: string
  ownerLogin: string
  ownerPassword: string
}

export async function needsSetup(): Promise<boolean> {
  const count = await prisma.location.count()
  return count === 0
}

export async function completeSetup(
  input: CompleteSetupInput,
): Promise<{ locationId: string; staffId: string }> {
  if (!(await needsSetup())) {
    throw new AppError(ErrorCodes.SETUP_ALREADY_COMPLETE, 409, 'Setup has already been completed')
  }

  const location = await prisma.location.create({
    data: {
      name: input.shopName,
      address: input.shopAddress,
      contractClauses: {
        create: DEFAULT_CONTRACT_CLAUSES.map((text, index) => ({ text, sortOrder: index })),
      },
    },
  })

  const staff = await prisma.staff.create({
    data: {
      name: input.ownerName,
      login: input.ownerLogin,
      passwordHash: await hashPassword(input.ownerPassword),
      role: 'owner',
      locationId: location.id,
    },
  })

  return { locationId: location.id, staffId: staff.id }
}
```

import { prisma } from '../db/client.js'
import { DEFAULT_CONTRACT_CLAUSES } from '../constants/defaultContractClauses.js'

async function backfillOrphanAllocations(): Promise<void> {
  const orphans = await prisma.allocation.findMany({
    where: { contractId: null },
    include: { product: true },
    orderBy: { createdAt: 'asc' },
  })
  if (orphans.length === 0) return

  const orphansByLocation = new Map<string, typeof orphans>()
  for (const orphan of orphans) {
    const list = orphansByLocation.get(orphan.product.locationId) ?? []
    list.push(orphan)
    orphansByLocation.set(orphan.product.locationId, list)
  }

  for (const [locationId, locationOrphans] of orphansByLocation) {
    const lastContract = await prisma.contract.findFirst({
      where: { locationId },
      orderBy: { number: 'desc' },
    })
    let nextNumber = (lastContract?.number ?? 0) + 1

    for (const orphan of locationOrphans) {
      const contract = await prisma.contract.create({
        data: {
          number: nextNumber,
          locationId,
          clientId: orphan.clientId,
          staffId: orphan.staffId,
          eventDate: orphan.checkoutDate,
          paymentMethod: '(não informado)',
        },
      })
      await prisma.allocation.update({ where: { id: orphan.id }, data: { contractId: contract.id } })
      nextNumber += 1
    }
  }
}

async function seedMissingClauses(): Promise<void> {
  const locationsWithoutClauses = await prisma.location.findMany({
    where: { contractClauses: { none: {} } },
  })
  for (const location of locationsWithoutClauses) {
    await prisma.locationContractClause.createMany({
      data: DEFAULT_CONTRACT_CLAUSES.map((text, index) => ({ locationId: location.id, text, sortOrder: index })),
    })
  }
}

export async function runContractBackfill(): Promise<void> {
  await backfillOrphanAllocations()
  await seedMissingClauses()
}

import { Prisma } from '../generated/prisma/client.js'
import { prisma } from '../db/client.js'
import { AppError } from '../errors/AppError.js'
import { ErrorCodes } from '../errors/errorCodes.js'
import { isOccupiedForRange, type AllocationWindow, type AllocationStatus } from '../domain/occupancy.js'

const MAX_WRITE_CONFLICT_RETRIES = 5
const ACTIVE_STATUSES: AllocationStatus[] = ['reserved', 'checked_out']

export interface CreateContractItemInput {
  productId: string
  checkoutDate: Date
  dueDate: Date
  priceCharged: number
}

export interface CreateContractInstallmentInput {
  dueDate: Date
  amount: number
}

export interface CreateContractInput {
  locationId: string
  clientId: string
  staffId: string
  eventDate: Date
  paymentMethod: string
  items: CreateContractItemInput[]
  installments: CreateContractInstallmentInput[]
}

function toWindow(allocation: { status: string; checkoutDate: Date; dueDate: Date; actualReturnDate: Date | null }): AllocationWindow {
  return {
    status: allocation.status as AllocationStatus,
    checkoutDate: allocation.checkoutDate,
    dueDate: allocation.dueDate,
    actualReturnDate: allocation.actualReturnDate,
  }
}

export async function createContract(input: CreateContractInput) {
  if (input.items.length === 0) {
    throw new AppError(ErrorCodes.VALIDATION_ERROR, 400, 'A contract needs at least one item')
  }
  for (const item of input.items) {
    if (item.dueDate.getTime() < item.checkoutDate.getTime()) {
      throw new AppError(ErrorCodes.DUE_DATE_BEFORE_CHECKOUT, 400, 'Due date must be on or after checkout date')
    }
  }

  const products = await prisma.product.findMany({ where: { id: { in: input.items.map((item) => item.productId) } } })
  const productsById = new Map(products.map((product) => [product.id, product]))
  for (const item of input.items) {
    const product = productsById.get(item.productId)
    if (!product) {
      throw new AppError(ErrorCodes.NOT_FOUND, 404, `Product ${item.productId} not found`)
    }
    if (product.status !== 'active') {
      throw new AppError(
        ErrorCodes.PRODUCT_NOT_IN_CIRCULATION,
        409,
        `Product is ${product.status} and cannot be allocated`,
      )
    }
  }

  const useSerializable = process.env.DB_PROVIDER === 'postgresql'

  for (let attempt = 0; attempt < MAX_WRITE_CONFLICT_RETRIES; attempt++) {
    try {
      return await prisma.$transaction(
        async (tx) => {
          for (const item of input.items) {
            const existing = await tx.allocation.findMany({
              where: { productId: item.productId, status: { in: ACTIVE_STATUSES } },
            })
            if (isOccupiedForRange(existing.map(toWindow), item.checkoutDate, item.dueDate)) {
              throw new AppError(
                ErrorCodes.PRODUCT_UNAVAILABLE,
                409,
                `Product ${item.productId} is not available for the requested dates`,
              )
            }
          }

          const lastContract = await tx.contract.findFirst({
            where: { locationId: input.locationId },
            orderBy: { number: 'desc' },
          })
          const nextNumber = (lastContract?.number ?? 0) + 1

          return tx.contract.create({
            data: {
              number: nextNumber,
              locationId: input.locationId,
              clientId: input.clientId,
              staffId: input.staffId,
              eventDate: input.eventDate,
              paymentMethod: input.paymentMethod,
              allocations: {
                create: input.items.map((item) => ({
                  productId: item.productId,
                  clientId: input.clientId,
                  staffId: input.staffId,
                  checkoutDate: item.checkoutDate,
                  dueDate: item.dueDate,
                  status: 'reserved',
                  priceCharged: item.priceCharged,
                })),
              },
              installments: {
                create: input.installments.map((installment) => ({
                  dueDate: installment.dueDate,
                  amount: installment.amount,
                })),
              },
            },
            include: { allocations: true, installments: true },
          })
        },
        useSerializable ? { isolationLevel: Prisma.TransactionIsolationLevel.Serializable } : undefined,
      )
    } catch (error) {
      if (
        error instanceof Prisma.PrismaClientKnownRequestError &&
        (error.code === 'P2034' || error.code === 'P2002')
      ) {
        continue
      }
      throw error
    }
  }

  throw new AppError(
    ErrorCodes.PRODUCT_UNAVAILABLE,
    409,
    'Could not complete contract creation due to repeated write conflicts, please retry',
  )
}
```

(The retry loop treats both `P2034`, serialization-failure under Postgres `Serializable` isolation, and `P2002`, a unique-constraint violation on `@@unique([locationId, number])` under any provider, as retryable — the DB-level constraint is defense-in-depth against exactly the race the in-transaction `findFirst`-then-`+1` numbering is meant to prevent, per the design spec's review notes; treating its violation as "retry" rather than "fail" is what makes it actual defense-in-depth instead of just a redundant assertion.)

export async function cancelContract(id: string) {
  const contract = await prisma.contract.findUnique({ where: { id } })
  if (!contract) {
    throw new AppError(ErrorCodes.NOT_FOUND, 404, `Contract ${id} not found`)
  }

  await prisma.allocation.updateMany({
    where: { contractId: id, status: 'reserved' },

  })

  return prisma.contract.findUniqueOrThrow({
    where: { id },
    include: { allocations: true, installments: true },
  })
}

export async function listContracts() {
  return prisma.contract.findMany({
    orderBy: { createdAt: 'desc' },
    include: { allocations: true, installments: true },
  })
