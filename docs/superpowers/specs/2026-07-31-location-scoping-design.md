# Location scoping — design

## Context

The schema models `Location` as a first-class multi-tenant boundary (`Staff.locationId`, `Contract.locationId` with `@@unique([locationId, number])`, `ProductPhotoToken.locationId`, per-location `maintenanceBufferDays`/`connectivityMode`), and `Contract` already enforces it correctly end to end. Most other resources don't:

- **Client**: no `locationId` column at all. `listClients`/`getClient`/`updateClient`/`deleteClient` are global.
- **Product**: has the column, but `listProducts`/`getProduct`/`updateProduct`/`deleteProduct` ignore it, and `createProduct` trusts a client-supplied `locationId` from the request body instead of deriving it from the session.
- **Allocation**: no direct `locationId` (reaches it via `productId → Product.locationId`); none of `checkOutAllocation`/`returnAllocation`/`cancelAllocation`/`getProductAvailability`/`isProductAvailableForRange`/`listAllocations` check it. Both `getProductAvailability`/`isProductAvailableForRange` and `productService`'s `availabilityFor`/`availabilityByProductId` bottom out in `server/src/services/occupancyQuery.ts` (`maintenanceBufferForProduct`, `loadBlockingWindows`), which trusts whatever `productId` it's handed with no location check of its own.
- **Calendar**: `listGoingOut`/`listDueBack`/`listOverdue` take no location parameter and aggregate across every location.
- **Contract → Client**: `createContract` validates `productId` against `input.locationId` but never validates `clientId` (nothing to validate against, today).
- **Product photos**: `GET /:id/photos/:filename` never checks that `:id` — or its location — matches the requested file; it only validates the filename pattern and reads straight off disk.
- **Relay resume**: `network/relayResume.ts`'s `relayCredentialsFromEnv()` calls `prisma.location.findFirst()` with the comment "single-location per install, matching resolveLocationId's existing assumption elsewhere" — the same class of gap, already present in production code, not just latent.

This is currently harmless in practice: `setupService.needsSetup()` guarantees exactly one `Location` row is ever created per install, so every "global" query today happens to return exactly the one store's data. The app is deployed as one Electron install per store today, but the schema is deliberately shaped for a future where multiple stores share one backend/DB, and this gap needs to be closed before that happens — without touching the one live store's data.

**Revision note:** this design has been through four adversarial review passes before implementation (see repo history for earlier versions). The first found the original migration plan could destroy the one live store's data on a failed-then-retried upgrade, among other gaps. The second found the first round of fixes included a genuine regression (an invariant guard that would have bricked every fresh install) and a recovery-path fix that looked plausible but didn't actually work end to end. The third found the manual-restore instruction didn't actually break the failure loop, the model registry test as specified couldn't pass, and the relay per-token fix was unreachable through its own boot path. The fourth found the same "restore doesn't break the loop" mistake reintroduced in a different spot (the guard-abort recovery path), a fix that would leave scratch schema objects behind on every successful migration, and a deny-by-default rule that would break `updateClient`'s own transaction. This version incorporates every fix from all four passes; see "Resolved from review" callouts inline.

## Goals

1. Every resource is scoped to the caller's location, consistently, with the same pattern `Contract` already uses.
2. Add a structural guardrail so a *new* route/model can't reintroduce this bug silently.
3. The schema migration (`Client.locationId`) is safe against the one live production SQLite database with real data: no data loss, no downtime beyond a normal update, and — critically — a **safe failure mode**. This design does not claim the migration cannot fail; it claims that if it does fail, nothing is lost and there is a real, working recovery path on the machine.

Out of scope: any product decision about cross-location access. The product direction is one login per location (no role-based, multi-account, or cross-location access model planned) — `Staff.role` already exists in the schema/JWT but currently gates nothing, and this design doesn't add any behavior that depends on it. If a cross-location or multi-account model is ever wanted later, that's a separate feature decision; nothing here forecloses it, but nothing here should be read as anticipating it either.

How this fits a future hosted/web deployment (as opposed to one Electron install per store) is still an open question, deliberately not answered here — every fix in this design (scoping by `Location`, the `scopedDb` guardrail, the Postgres schema already tracking the SQLite one) is deployment-shape-agnostic on purpose, so it doesn't block that direction, but the specifics (how a login maps to a location on the web, single shared login page vs. one per store, etc.) belong to that design when it's actually being built.

## Design

### 1. Migration safety prerequisites (do these *before* authoring the `Client` migration)

The review found the app's existing safety nets don't actually hold up against a failure in a migration this size. These are prerequisites, not nice-to-haves — the `Client` migration should not be authored until they land, because it's the first migration whose failure mode they're inadequate for.

**1a. The pre-migration backup destroys itself on retry — fix first.**

`client/electron/backup.ts`'s `backupDatabaseIfNeeded` keys its backup directory by `<oldVersion>` and calls `fs.rmSync(destDir, { recursive: true, force: true })` before recopying, on the documented assumption ("Keyed by `<oldVersion>` alone and overwritten on retry: a failed migration is transactional (DB untouched)...") that a failed migration never touches `dev.db`. That assumption is false: `server/src/db/migrationRunner.ts` runs each migration script with **no wrapping transaction** (required — SQLite's `PRAGMA foreign_keys=OFF`, needed for the table-rebuild pattern below, is a silent no-op inside a transaction), and `better-sqlite3`'s `db.exec()` commits statements as it goes. Concretely: `backupDatabaseIfNeeded` copies `dev.db` → `backups/<oldVersion>/`; `runMigrations` fails partway through the `Client` rebuild (say, after `DROP TABLE "Client"`, before `RENAME`); the marker never advances; on relaunch, `backupDatabaseIfNeeded` computes the *same* `destDir`, deletes the one good backup, and overwrites it with the now-corrupted `dev.db`.

Fix: `backupDatabaseIfNeeded` must not delete an existing `destDir` and replace it with a new copy when retrying after a failure. **Resolved from second review:** "skip if `destDir` already exists and is non-empty" is not sufficient on its own — it doesn't distinguish a complete prior backup from one truncated by the *backup copy itself* failing partway (disk full, AV lock mid-`copyFileSync`; `startServer` already deliberately aborts if the copy throws, at `main.ts:326-332`, which is exactly the case that would leave a partial `destDir`). The backup step needs a completion signal, not an emptiness check: copy into a temporary directory and `fs.renameSync` it into place only after every file has copied successfully (rename is atomic on the same filesystem), or write a sentinel file last and treat its absence as "incomplete, redo." Either way, a retry must only ever skip a *provably complete* prior backup.

**Resolved from third review — two implementation gaps in that fix:**
- **The staging directory must not live inside `backups/`.** `pruneBackups` (`backup.ts:60-72`) enumerates every directory under `backups/` and evicts anything past the 5-slot retention by mtime — a staging dir counts against those 5 slots and can evict a real backup, or be pruned mid-copy. Stage it as a sibling of `backups/` on the same filesystem (so the final `renameSync` stays atomic) and only move it under `backups/` once complete.
- **§1c's process-exit wait must cover the backup step too, not just migrations.** As drafted, §1c only guards `runMigrations`. But `backupDatabaseIfNeeded` runs *first* and copies `dev.db` + `-wal`/`-shm` as three separate, non-atomic `copyFileSync` calls — if the previous process is still writing during those copies, every individual copy can still succeed while the result is internally inconsistent, and the completion signal would then certify a torn backup as "complete." The old-process wait belongs before the backup step, not just before the migration.

Also update the stale comment at `backup.ts:22-30` itself (the one asserting "a failed migration is transactional... overwritten on retry") as part of this fix — it states the exact false assumption being corrected, and should not survive the fix describing something the new code no longer does.

**Resolved from fourth review — the atomic-rename design has a rollout gap: every backup directory that exists in the field today predates the completion signal.** The very first time an updated app runs this new code against an existing `backups/<dir>/` written by the old, non-atomic `backupDatabaseIfNeeded`, that directory has no sentinel and can't be proven complete — and `fs.renameSync(staging, destDir)` fails outright (`ENOTEMPTY`/`EPERM`) when `destDir` already exists and is non-empty, which would abort startup on the very next update after this ships. Deleting `destDir` first to make room is exactly the data-destroying move this whole fix exists to prevent, because that legacy directory might hold the one good pre-migration copy. Fix: if `destDir` exists but isn't provably complete (no sentinel/wasn't produced by an atomic rename), move it aside (e.g. `<destDir>.unverified-<timestamp>`) rather than delete or overwrite it, and let it fall out of `backups/` on its own via `pruneBackups`' normal retention. Also note: nothing currently cleans up a staging directory abandoned by a crash between copy and rename — the next attempt should reuse or discard a stale staging dir rather than accumulate one per crash.

**1b. The documented recovery path doesn't exist on the live machine.**

`migrationRunner.ts`'s failure message and this design's first draft both pointed at `prisma migrate resolve`. The packaged app does not ship the Prisma CLI (`client/electron-builder.yml`'s `extraResources` is an explicit allowlist of native modules and `.sql` files only) — that command does not exist on the store's machine. `migrationRunner.ts`'s own failure-message text must stop naming it (see rollout, §7).

**Resolved from second review — the "bridge into the existing restore UI" fix from the first revision doesn't work and has been dropped.** It looked plausible but fails on inspection of the actual restore path: after a migration failure, `main.ts` shows the error dialog and calls `app.quit()` **before** the window or the `backup:restore` IPC handler are ever created, so there is no UI to reach; even if there were, the restore screen lives behind login, which needs the very server that just failed to start; and the restore function only knows how to consume an *online snapshot* (`db.backup()`, taken by a running server), not the pre-migration backup's raw-file-plus-WAL-sidecar copy — feeding one to the other silently discards uncommitted WAL data. Building a real fix here (a recovery UI that works without login, the Express server, or even a fully-started app) is a genuinely separate, larger project, not a fix that folds into this one — see "Deliberately out of scope" below.

**Decision: for this pass, recovery is a documented manual restore, not an in-app flow.** The safety property this design actually guarantees is "if the migration fails, your data is provably intact on disk at a known location" — not "one click fixes it." The startup-failure dialog (already shown before `app.quit()`, so this part *is* reachable — `showErrorBox` works with no window once the app is ready) must state the exact backup path and instruct the operator how to recover.

**Resolved from third review — two things the prior draft of this decision got wrong:**

- **The stated path was wrong, and the dialog can't just print a hardcoded pattern.** `backupDatabaseIfNeeded`'s `destDir` is keyed by `marker ?? \`pre-updater-${today}\`` — the *previous* version (or a dated fallback for marker-less legacy installs) — not `app.getVersion()` (the *new* version), so "`userData/backups/<version>/`" as written reads as the wrong one. The dialog must be given the actual path, which means: `startServer` must capture `backupDatabaseIfNeeded`'s return value (currently discarded); the "skip, already complete" branch added in 1a must still return the existing `destDir` (not `null`) so a second or later failed retry's dialog can still state it; and the dialog must handle the true-fresh-install case, where there's nothing to back up and `backupDatabaseIfNeeded` correctly returns `null` — no path should be printed there.
- **Restoring the backup alone doesn't end the failure loop, and the instruction must say so.** The backed-up `dev.db` predates the failed migration, so restoring it and relaunching the *same app version* reruns the identical migration and fails identically — restoring data isn't restoring a working app. The dialog's guidance must include the step that actually breaks the loop. **Resolved from fourth review — "roll back to the previously-installed version" is not a real option here and shouldn't be offered as one.** The app installs via NSIS in place, with no `allowDowngrade` configured anywhere, updating through an authenticated private Worker proxy — there is no old build left on disk for an operator to reinstall. The guidance should lead with **contact support**, not a conditional rollback step that's very unlikely to be available. This is also why the invariant-guard abort in §2 step 1 needs its own explicit recovery note — see there, and note it is *not* the "restore and retry" case: restoring only helps a transient mid-migration failure, not a guard trip caused by the data itself being invalid.
- **The instruction must also cover stale sidecars, not just the main file.** `manualBackupActions.ts`'s own restore logic treats this as load-bearing (it explicitly deletes `dev.db-wal`/`-journal`/`-shm` before restoring, so a stale sidecar from the just-failed run can't get replayed against the restored file). A manual "copy `dev.db` and its sidecars back" instruction needs the same care: it must tell the operator to remove the *current* `dev.db-wal`/`dev.db-journal`/`dev.db-shm` (left by the failed run) before or while copying the backed-up files over, not just overwrite `dev.db` and leave those in place.

**Deliberately out of scope for this pass, tracked as a follow-up:** a real offline-capable recovery screen — one that can restore the raw pre-migration backup without needing login, the Express server, or a fully-started app, likely extending the existing pattern used for the activation-failure screen (the one other place this app already renders UI when the normal server/window stack can't come up). This is a legitimate future improvement, not a blocker for shipping the location-scoping work with the documented-manual-restore safety net in place.

**1c. Migrations run before the previous process is confirmed gone — reduces the odds of hitting 1a/1b at all.**

`client/electron/main.ts`'s `startServer` calls `backupDatabaseIfNeeded` then `runMigrations` (line ~328-333) before `waitForPortFree` (line ~347) — and `waitForPortFree` is a *network port* probe for the *new* server's own bind, not a wait for the *old* process to release its file handle on `dev.db`. The file already has a comment acknowledging this exact race for the restore path (`waitForProcessExit`'s comment: "unlike waitForPortFree's existing use for the *next* server's startup, there was previously nothing making the *current* restore wait for the *old* server to actually be gone first") — the same gap exists for migrations, and migrations are the largest write this app has ever done to `dev.db`. On an `electron-updater` restart, the new instance can reach `runMigrations` while the old process still holds the file, risking `SQLITE_BUSY` mid-rebuild — precisely the failure mode 1a/1b need to survive. Fix: wait for the previous process to actually be gone (or retry-with-backoff on a locked file, mirroring `waitForPortFree`'s probe loop) before `runMigrations` starts. **Resolved from fourth review, narrowing which mechanism actually applies here:** the existing `waitForProcessExit` helper takes a `ChildProcess` handle, which only works when *this* process spawned the one it's waiting on — on an `electron-updater` restart, the new app instance has no handle to the old instance's process at all, so `waitForProcessExit` itself isn't reusable for this case (it's the right tool for the restore flow, which does hold that handle). The retry-with-backoff-on-a-locked-file approach, mirroring `waitForPortFree`'s probe loop, is the one actually implementable here.

### 2. Schema migration: `Client.locationId`

Add a required `locationId` (FK to `Location`) to `Client`, targeting SQLite (the live store's provider) first, generating the equivalent Postgres migration (`npm run db:migrate:postgresql`) alongside it so the two provider schemas — generated from the same `models.prisma` — don't silently diverge, even with no live Postgres deployment today.

**Resolved from review:** `prisma migrate dev` does not generate the migration this design needs. Its auto-generated rebuild for a new required column omits that column from the `INSERT INTO "new_Client" (...) SELECT ...` clause, which fails with a `NOT NULL` constraint violation against any non-empty table. This script must be **hand-authored**, using the CLI output only as a starting skeleton, and reviewed against this design, not trusted as generated.

The migration must, in order:
1. **Assert the invariant this whole plan depends on, rather than trust it — first, before touching the schema.** The script must hard-fail (not silently proceed) if **more than** one `Location` row exists. **Resolved from second review, fixing a regression in the prior draft:** the guard must be `COUNT(*) > 1`, not "exactly 1"/`<> 1` — migrations run at first launch, before `completeSetup` ever creates a `Location`, so a brand-new install (and every CI/test DB before seeding) has zero `Location` rows at migration time; an "exactly 1" guard would abort on every fresh install and brick first-run setup permanently. Zero or one `Location` rows are both fine (an empty `Client` table has nothing to mis-backfill either way, and `Client` cannot be non-empty while `Location` is empty — client creation requires an authenticated `Staff`, which requires a `Location`); only *more than one* is the unsafe case. `RAISE()` only works inside a trigger body in SQLite, not as a plain statement, so the guard needs a small trigger-based construct (e.g. a scratch table with a `CHECK`/trigger fed by the count).
   - **Resolved from third review — the cleanup for that scratch construct was underspecified.** Both the scratch table *and* the trigger need `CREATE ... IF NOT EXISTS` / `DROP ... IF EXISTS` guards (the original draft only mentioned the table).
   - **Resolved from fourth review — cleanup needs to run at *both* ends, not just moved to the front.** The third-review fix over-corrected: "cleanup before creation, not after" is right for handling residue from a *previous aborted* run (an idempotent `DROP ... IF EXISTS` first, so `CREATE` never collides with leftover debris), but dropping the trailing cleanup entirely means every **successful** run permanently leaves the scratch table and trigger behind in production — the cleanup that removes them on the happy path was cut along with the "dead code on the abort path" fix. The correct shape is cleanup at both ends: idempotent `DROP ... IF EXISTS` first (handles a prior abort's leftovers), create the guard construct, run the check, then `DROP ... IF EXISTS` again immediately after — the second `DROP` only ever executes on success (an abort mid-script never reaches it, which is fine, because a subsequent retry's leading `DROP ... IF EXISTS` cleans it up then). This is also what makes the "resulting schema matches `models.prisma`" test (Testing, below) actually able to pass.
   - **Resolved from third review, corrected in fourth — an aborted guard has a real consequence, but restoring the backup does not fix it.** After an abort, user tables (`Client`, etc.) are genuinely untouched, but an unresolved `_prisma_migrations` row (`finished_at`/`rolled_back_at` both `NULL`) persists, and `migrationRunner.ts:87-93` refuses to run **any** migration on every subsequent launch until it's resolved. The third revision claimed restoring the pre-migration backup "clears the block and allows a clean retry" — that's wrong: the backup contains the *same* two-or-more `Location` rows that tripped the guard in the first place, so relaunching the same version reruns the identical migration, and the guard fires again with a fresh unresolved row. This is the same "restoring data doesn't restore a working app" mistake §1b's manual-restore text made and fixed — reintroduced here. Because this guard should never fire in production in the first place (the invariant holds structurally today; see below), the honest recovery statement is: this is not a transient failure a restore can fix — it means the invariant this whole migration depends on is actually violated, and someone needs to either correct the data (resolve which `Location` is canonical and remove/merge the others) or contact support. Restore-then-retry is not a valid recovery path for this specific failure, unlike a transient mid-rebuild failure (which restore-then-retry *does* fix, since nothing about the data caused it).
2. Add the column nullable.
3. `UPDATE "Client" SET "locationId" = (SELECT "id" FROM "Location" LIMIT 1)`.
4. Rebuild the table (SQLite "RedefineTables" pattern: create new table with the column `NOT NULL` + FK, copy, drop old, rename) with `PRAGMA foreign_keys=OFF` around it.

With 1a/1b fixed, an aborted migration at step 1 is a *safe* failure — recoverable via the documented manual restore (§1b), not silently wrong data.

This exact rebuild-with-dependent-FKs shape is already proven safe by this runner: `prisma/sqlite/migrations/20260727171057_add_location_maintenance_buffer` rebuilds `Location` itself, which is referenced by five other tables (two with `ON DELETE CASCADE`), and has already shipped successfully. That's the precedent to build from, not a first attempt at this pattern.

Before this migration ships:
- Hand-verify the script (not just trust CLI output — see above).
- Test it against a throwaway copy of realistically-shaped SQLite data (existing dev/e2e seed data, not an empty DB), including a deliberate multi-location test to confirm the invariant guard actually aborts cleanly.
- Prompt the live store's operator to take a manual backup before installing the release containing this migration — on top of the tested script and the completion-safe automatic backup (1a) with its documented manual-restore path (1b), not a substitute for either.

**Rollout note:** this migration and the `Client`-service code that depends on the column being present (`clientService.createClient`, etc.) must ship in the **same release**. A `Client.locationId` column that's `NOT NULL` breaks `createClient` immediately if the code isn't updated in lockstep — there's no safe way to ship the schema change alone first.

**Dropped from scope (resolved from review):** the earlier draft proposed also moving `Staff.login` from `@unique` to `@@unique([locationId, login])`. Dropped: it breaks `authRoutes.ts`'s `prisma.staff.findUnique({ where: { login } })` (login stops being a valid unique-where target), and the login form only ever sends `login` + `password` with no location to disambiguate by if two locations shared a login — an unresolvable ambiguity under the current one-login-per-location, no-cross-location-model product direction. It buys nothing today and the "how do logins map to locations" question is explicitly deferred to the future hosted-deployment design anyway (see Goals). Not included.

**Invariant enforcement (non-blocking, worth doing in the same pass):** the one-Location invariant holds in every packaged build today (`server/scripts/db-tools.ts` and seed scripts are dev-only — not bundled by `electron-builder.yml`, not imported from `src/`) but is enforced only by convention: `setupService.needsSetup()`/`completeSetup()` is a check-then-create with no transaction, and `POST /api/setup` (`routes/setup.ts`) has no auth middleware, so a double-submitted setup wizard could race two `Location` creations. The migration's invariant guard (step 1, above) turns a violation into a safe abort rather than silent corruption; consider also hardening `setupService` itself (a transaction, or a partial unique constraint) as a follow-up, since a broken invariant would still block the app from ever completing this migration until fixed.

### 3. Auth middleware: centralize `locationId` resolution

`requireAuth` (`server/src/auth/authMiddleware.ts`) fetches `Staff` once per request and sets `req.staff = { staffId, role, locationId }`. This replaces the equivalent per-route `locationId` lookups duplicated in `routes/contracts.ts` (`resolveLocationId`), `routes/locationSettings.ts`, and `routes/products.ts` (its own `staff.findUniqueOrThrow` calls); every router gets `locationId` without its own DB lookup.

**Noted from second review, deliberate trade-off:** `requireAuth` today is pure JWT verification and never touches Prisma; this change adds a real DB round trip to every authenticated request, including the ~4-minute SSE ticket poll. The alternative — embed `locationId` directly in the JWT, as `mintSseTicket`/`issueProductPhotoSession` already do for their own short-lived tokens — avoids that, at the cost of a staleness window if a staff member's location ever changes before their token renews. Given this app's actual traffic (one local shop, requests measured in single digits per minute, an indexed primary-key lookup), the extra query is negligible; the JWT-embed approach is the one to revisit if this is ever adapted for a higher-traffic hosted deployment.

### 4. Guardrail layer

**Resolved from review:** the original design claimed a `scopedDb(locationId)` Prisma `$extends` wrapper would make "the unscoped path... not reachable from route code." That's not achievable, and the design should not claim it is:
- Query extensions intercept only **top-level delegate calls**. Nested reads/writes (`contractService.getContract`'s `include: { client: {...} }`, `clientService.createClient`'s nested `identityDocuments`/`addressLines` creates) don't go through the extension at all and need manual review, not automated coverage.
- `productService.ts`/`clientService.ts` also call `prisma.allocation.*` directly for history/join checks — they can't stop importing the bare `prisma` client, so "routes stop importing bare `prisma`" doesn't hold at the service layer either. Import discipline alone isn't the guardrail; treat it as one layer, backed by a lint rule (an `ast-grep` pattern flagging a bare `prisma.client`/`prisma.product` call outside `scopedClient.ts` itself) as defense in depth.
- The original operation list (`findMany`/`findUnique`/`update`/`delete`/`updateMany`/`deleteMany`) omits operations this codebase actually uses against these models: `findFirstOrThrow`, `findUniqueOrThrow` (e.g. `products.ts`, `contracts.ts`, `allocationService.ts` all use `OrThrow` variants), `count`, `upsert`, `create`, `createMany`. An allow-list of only some operations means a new call using an unlisted one silently passes through unscoped — the opposite of the intended guardrail.

Revised design: `server/src/db/scopedClient.ts` builds `scopedDb(locationId)` using Prisma's `$allOperations` extension hook with an explicit **deny-by-default** switch — every operation this codebase performs against `client`/`product` (`findMany`, `findFirst`, `findFirstOrThrow`, `findUnique`, `findUniqueOrThrow`, `create`, `update`, `updateMany`, `upsert`, `delete`, `deleteMany`, `count`) gets `locationId` merged into its `where`/`data` as appropriate, and any operation not explicitly handled **throws** rather than passing through. `prisma.$transaction` call sites that need scoping (e.g. `clientService.updateClient`'s transaction) must be given the extended client instance, not the bare one, so writes inside the transaction stay scoped too.

**Resolved from second review:** as written, this only covers `client`/`product` — a *new* model with its own `locationId` column gets zero protection from either the extension or the `ast-grep` rule below, which undercuts Goal 2's "a new route/model can't reintroduce this bug silently." Fix: make the model list itself a maintained registry (`LOCATION_SCOPED_MODELS = ['client', 'product']` today) that both the `$allModels`-wide extension and the lint rule read from.

**Resolved from third review — the registry-matches-schema test as first specified cannot pass, and needs an explicit exclusion list instead of a flat equality check.** Once §2 lands, `models.prisma` carries a `locationId` column on **six** models, not two: `Staff`, `Product`, `Contract`, `ProductPhotoToken`, `LocationContractClause`, and `Client`. `LOCATION_SCOPED_MODELS` can't simply grow to match all six — `Staff` must be queried unscoped at login (`authRoutes.ts`'s `findUnique({ where: { login } })` runs before any location is known), `ProductPhotoToken` is looked up by token on unauthenticated paths with no `req.staff`, and `Contract`/`LocationContractClause` are already scoped by hand via their own explicit `where: { locationId }` clauses rather than `scopedDb`. So a bare `registry == locationId-bearing models` test would fail immediately and isn't the right check.

The correct version: maintain `LOCATION_SCOPED_MODELS` (models routed through `scopedDb`) alongside an explicit, commented `MANUALLY_SCOPED_MODELS` list (`staff`, `contract`, `locationContractClause`, `productPhotoToken` — each with a one-line reason, e.g. "queried before a location is known"). The test asserts `LOCATION_SCOPED_MODELS ∪ MANUALLY_SCOPED_MODELS` equals the full set of `locationId`-bearing models in `models.prisma` — so a new model lands in neither list only if someone forgets it entirely, which is exactly the failure Goal 2 needs to catch, while a model that's deliberately scoped a different way (like `Contract`) doesn't force a false failure.

One more thing this needs to state explicitly: what the `$allModels`-wide extension does for a model that's in neither list. **Resolved from fourth review — "throw for any model in neither list" breaks a real call site and needs narrowing.** `clientService.updateClient`'s transaction (line 108, above) is itself scoped by using the extended client for `$transaction`, and inside that transaction it writes `tx.clientIdentityDocument`/`tx.clientAddressLine` — models with no `locationId` column at all, so by construction they can't be (and shouldn't be) in either `LOCATION_SCOPED_MODELS` or `MANUALLY_SCOPED_MODELS`. A blanket "throw for anything in neither list" makes that transaction fail on its first write. The rule instead has to be: **throw only for a model that (a) carries a `locationId` column per `models.prisma` and (b) is in neither list.** A model with no `locationId` column at all (`ClientIdentityDocument`, `ClientAddressLine`, `Allocation`, `Location`, etc.) passes through unmodified — there is nothing to scope and nothing to forget, so it isn't a Goal-2 risk. `Allocation`/`Calendar`'s `where: { product: { locationId } }` pattern (below) is a separate mechanism entirely — a join-based filter applied by the calling code, not something routed through `scopedDb` — and needs no entry in either list under this narrower rule.

**Also from fourth review:** the `ast-grep` lint rule ("bare `prisma.client`/`prisma.product` outside `scopedClient.ts`") as described would also flag legitimate non-request-context call sites like `productPhotoTokenService.ts`'s direct `prisma.product` lookups. Either name an explicit exemption mechanism for call sites like that (a lint-ignore comment, or a short allowlist in the rule itself), or move those sites to `scopedDb(photoToken.locationId)` too, since they already have a `locationId` in hand from the token row — the latter is preferable where it's a straightforward change, since it closes the exemption rather than widening it.

`Allocation`/`Calendar` reach location through the `product` relation (a join, not a column), which the extension can't cover — they keep explicit `where: { product: { locationId } }`, matching `contractService.ts`'s existing pattern. `occupancyQuery.ts`'s helpers (`maintenanceBufferForProduct`, `loadBlockingWindows`) take a bare `productId` with no location check of their own by design — every caller (`allocationService.getProductAvailability`/`isProductAvailableForRange`, `productService.availabilityFor`/`availabilityByProductId`) must only ever pass a `productId` it has already verified belongs to the caller's location.

Shared test setup seeds **two** locations with data in each by default, plus one reusable "staff at location A can't see/touch location B's resource" assertion run against every resource type (client, product, allocation, calendar, contract, product photo). This is what turns a future missing filter into a failing test instead of a silent gap invisible in single-location dev/test data — the exact condition that let this go unnoticed in the first place.

### 5. Per-resource changes

- **Client**: `locationId` column (§2); `listClients`/`getClient`/`updateClient`/`deleteClient` scoped via `scopedDb`; `createClient` takes `locationId` from `req.staff`, not the request body.
- **Product**: same query shape via `scopedDb`. `createProduct` stops trusting a client-supplied `locationId` in `POST /api/products`'s body — **the derivation happens at the route** (`routes/products.ts`), not inside `productService.createProduct` itself: the service keeps taking `locationId` as an explicit parameter, because it already has legitimate non-HTTP callers that pass their own resolved `locationId` — `productPhotoTokenService.ts`, and `listProductsForLocation` from `signingApp.ts`/`network/relayClient.ts` — none of which have a `req.staff` to derive from.
- **Allocation**: `checkOutAllocation`/`returnAllocation`/`cancelAllocation`/`getProductAvailability`/`isProductAvailableForRange`/`listAllocations` take `locationId`, checked through the `product` relation, 404 on mismatch.
- **Calendar**: `listGoingOut`/`listDueBack`/`listOverdue` take `locationId`, filtered via `product: { locationId }`.
- **Contract → Client**: `createContract` adds `client.locationId !== input.locationId → 404`, mirroring the existing product check. (Ordering is fine: this depends only on the `Client.locationId` column existing, which §2 already guarantees before this lands.)
- **Product photos**: `GET /:id/photos/:filename` loads the product by `:id`, checks it belongs to `req.staff.locationId`, and confirms the requested filename is actually one of that product's own `photos` entries before serving it from disk.
- **Relay resume**: **Resolved from fourth review — the third-revision fix described `relayCredentialsFromEnv()` two contradictory ways in the same paragraph (gains a `locationId` parameter for request-context callers, but also loses its mode check "entirely").** Checking the actual call sites resolves it: `routes/products.ts` and `routes/contracts.ts` **already** resolve their own location and check `connectivityMode === 'relay'` themselves *before* calling `relayCredentialsFromEnv()` — so the function doesn't need a `locationId` parameter or any mode check of its own at all. `relayCredentialsFromEnv()` becomes pure, location-independent env resolution (`url`/`productKey`/`installId` only, no Prisma call). Its boot-time caller (`server.ts`) passes the resolved credentials straight to `resumeRelayConnections`, which is where the real per-token fix lives: **resolved from third review**, the previous design gated the *entire* boot-time resume on one arbitrary location's mode (`relayCredentialsFromEnv()` returning `null` whenever that one location happened to be `'lan'`, silently dropping every other location's `relay` tokens) — `resumeRelayConnections` now checks each `ProductPhotoToken`'s *own* location's `connectivityMode === 'relay'` before resuming that specific token, so no single location's setting gates any other's.

**Reviewed, intentionally unchanged (with one caveat):**
- `contractBackfill.ts` runs once at every boot and repairs orphaned allocations across the *entire* database as a maintenance sweep, not a per-request read — it's correctly location-agnostic by design, not a missed gap. **Caveat added from second review:** it sets the repaired `Contract`'s `locationId` from the allocation's *product*, and its `clientId` from the orphan allocation, with nothing asserting the two agree. Once `Client.locationId` exists and `createContract` enforces client/product location agreement for *new* allocations (§5), this can't happen going forward; it's a purely historical risk (every allocation to date belongs to the one location that's ever existed) but worth a defensive check — skip and log rather than silently create a cross-location `Contract` — as cheap insurance once multiple locations are real.
- `backupService.ts`'s `POST /api/backup/snapshot` dumps the whole database file (already refuses on Postgres). Fine for a single-location install; a real cross-tenant risk in a future hosted deployment. Left as-is here — same reasoning as the rest of "hosted deployment" being out of scope — but flagged so it isn't forgotten when that design happens.

### 6. Mismatch response

A resource that exists but belongs to another location returns `404 Not Found`, identical to "doesn't exist" — matches `contractService.ts` today, and doesn't leak that an ID is valid at another location.

### 7. Rollout sequencing

1. Migration safety prerequisites (§1a/1b/1c) — the atomic/completion-signal backup-on-retry fix (including its stale `backup.ts` comment and the staging-dir/`pruneBackups` interaction), the failure dialog stating the correct manual-restore path and the actual loop-breaking step (and `migrationRunner.ts`'s failure text no longer naming `prisma migrate resolve`), and the file-lock/process-exit ordering fix extended to cover the backup step as well as migrations. These are infrastructure this migration leans on; they land first, independent of everything else here.
2. Schema migration (§2) — `Client.locationId` (and its Postgres counterpart) — **together with** the `Client`-service code changes that depend on the column, hand-verified and soak-tested against realistic data, including a deliberate multi-location invariant-guard test.
3. Guardrail layer (§4: `scopedDb` deny-by-default + two-location test fixtures + the `ast-grep` bare-`prisma` lint check).
4. Per-resource fixes one at a time — Product → Allocation/Calendar → Contract's client check → product photo endpoint → relay resume — each landing with its own cross-location isolation tests green before the next starts. (Client's route/service changes already landed as part of step 2.)
5. Ship as one release; prompt for a manual backup before the update installs, on top of the tested migration and the completion-safe automatic backup.

**Deliberately out of scope for this pass:** a real offline-capable recovery screen that can restore without login/server/window (§1b). Tracked as a follow-up, not a blocker for this release.

## Testing

- Cross-location isolation test per resource (list/get/update/delete/create, plus the photo endpoint) using the two-location fixture: staff at location A gets 404 (or an empty list) for location B's data.
- Migration test: apply the hand-authored SQL against a copy of seeded (non-trivial) SQLite data and assert every pre-existing `Client` row ends up with the correct (sole) `locationId`, and that the resulting schema matches `models.prisma`.
- Migration invariant-guard tests: (a) a **fresh, empty** DB (zero `Location` rows) must migrate successfully — regression test for the "exactly 1" bug caught in review; (b) seeding **two** `Location` rows before applying the migration must abort cleanly (no partial schema change, clear error) rather than mis-assigning data.
- Backup completion-signal test: simulate the backup copy itself failing partway (e.g. one `copyFileSync` throwing), relaunch, and assert the retry redoes the backup rather than treating the truncated copy as complete.
- Backup-safety regression test: simulate a migration failure partway through *after* a complete backup, relaunch, and assert the original pre-migration backup still exists and is intact — not overwritten by the failed attempt.
- Regression coverage for `createProduct` (server-derived `locationId` at the route, request-body value ignored/rejected) and `createContract` (client/location mismatch now 404s).
- `scopedDb` unit tests: confirm every operation this codebase uses against `client`/`product` is explicitly handled, that calling an unhandled operation throws rather than silently executing unscoped, that a model in neither `LOCATION_SCOPED_MODELS` nor `MANUALLY_SCOPED_MODELS` throws, and that the union of both lists matches every `models.prisma` model with a `locationId` column.
- Backup staging test: assert the temporary/staging copy directory is never visible to `pruneBackups` and is never evicted mid-copy by the 5-slot retention.
- Guard-abort test: force the invariant guard to fire (seed two `Location` rows), confirm the resulting unresolved `_prisma_migrations` row blocks subsequent launches as expected, and confirm that a *successful* run (single `Location`, no guard trip) leaves no scratch table/trigger behind and the resulting schema matches `models.prisma` — this guard firing in production is not expected to be recoverable by restore-and-retry (see §2), so there's no "clean retry after restore" case to test here, only that the schema stays clean when the guard doesn't fire.
- Relay resume test: seed two locations with different `connectivityMode` values (one `lan`, one `relay`), each with a live `ProductPhotoToken`, and confirm boot-time resume opens a connection for the `relay` location's token **and does not** open one for the `lan` location's token — asserting only the positive case would pass even with no per-token filter at all.
